Where I’m Useful

AI programs stall for predictable reasons. The value case never survives scrutiny. Nobody defines what the system is allowed to do. The organization has no obvious place to start. I work embedded with client teams on all of it, holding both the technical design and the business argument, which is the pairing that keeps a program alive past its first review.

01

Making the case AI actually gets funded on

I build the ROI and value models that hold up under a CFO’s scrutiny: where the cost comes out, when it lands, and which assumptions the whole number rests on. Then I sit in the room and defend them. That last part is where most value cases come apart.

$500M+in enterprise pursuits won on value cases I built or contributed to
02

Building agents, and the security model they need

I build agents hands-on, where the security model is the hard part. An agent acting on live systems for a specific person has to inherit that person’s permissions and stop there. Data coming back from a tool has to be fenced so the model treats it as information rather than instructions. Anything that writes needs a human confirming first. I design and implement those controls.

Hands-onagent orchestration, scoped authorization, prompt-injection defense

Running security programs at enterprise scale

I run large security programs for enterprise clients. Most of the difficulty is coordination: competing stakeholders, unclear ownership, and controls that nobody sequenced against the delivery date. Treating security as a design input from the start costs a fraction of what it costs to retrofit two weeks before launch.

About
01
Writing the code stopped being the bottleneck. Knowing what to ask for, and recognizing when what comes back is confidently wrong, is the job now.

I’m a Managing Consultant at IBM working on enterprise AI and cybersecurity. I run large programs for major clients, and I build the agent systems myself. Those two things almost never live in the same person, and the gap between them is where most AI investment quietly dies: architecture nobody can justify, or business cases nobody can build.

The agentic shift changed what technical work rewards. For a decade the prized engineer was the meticulous one, careful with every line. That skill is now table stakes. The work today is decomposition, delegation, and verification: framing a problem precisely enough that a system can act on it, engineering the context it needs to act well, and holding a high enough bar to catch output that is fluent and wrong. Those are management skills. The people adapting fastest are the ones who already knew how to set a brief, delegate it, and inspect what came back.

I’ve spent years translating between the engineers who build systems and the executives who fund them, which turns out to be the same shape as directing an agent: set the goal, bound the authority, judge the result against what the business actually needed. I work across automotive, manufacturing, and energy & utilities, with an MBA from Michigan Ross in strategy and finance, IBM’s Advanced credential in Generative & Agentic AI, and Gold-level industry certification in Automotive.

What I’m Building Now
Agent Engineering

How I Build Agents That Touch Real Systems

Agentic AI MCP Least Privilege Least Agency

A demo agent is a model and a few tools. An agent allowed near production systems is a distributed system with an untrusted natural-language interface. This is the reference architecture I build to, with each boundary mapped to the threat it exists to stop.

The boundaries do the work. Every natural-language input arrives untrusted, including retrieved documents and messages from other agents. The agent carries the calling user’s permissions and no more. High-impact actions stop for a person. And everything is logged well enough to reconstruct afterward what the agent did and why it decided to.

Open Problems I’m Watching

Expert fingerprinting in MoE routing

Mixture-of-experts models route each token to a handful of specialists, invisibly. Latency and failure patterns leak that routing anyway. Probe long enough and you can map which expert handles what, then target the weakest safety behavior. Reconnaissance rather than exploit, which is why it falls off threat models.

Identity systems built for people, not agents

Provisioning, rotation, and deprovisioning all assume a human on the other end. Give a thousand agents scoped credentials and the directory quietly becomes the largest unmanaged identity surface in the company. Each holds real authority, and nobody has built a process for offboarding one.

Poisoned context outliving the session

Most evaluation catches single-turn failures. A corrupted memory or retrieved document persists instead, shaping decisions days later with no obvious link back to the injection that caused them. That distance between where harm surfaces and where it entered is the whole problem.

Tool provenance as a supply chain

An agent’s capability surface is now effectively a package manifest. Every connected tool is code you did not write, executing with your users’ authority against your real systems, and the ecosystem ships far faster than any review process has managed to keep up with.
